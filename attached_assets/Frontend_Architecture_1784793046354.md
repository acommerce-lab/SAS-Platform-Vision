## 1. المبدأ العام

وفق ADR-004 في Product Constitution: فصل كامل بين الواجهة الأمامية والخلفية عبر API واضح (لا Server-rendered Monolith)، لإتاحة إضافة واجهات مستقبلية (تطبيق جوّال) تستهلك نفس الـ API دون تعديل الخلفية.

## 2. هيكل المشروع المقترح

```
/src
  /pages (أو /routes)
    /auth            ← تسجيل دخول، تسجيل ذاتي
    /admin            ← لوحة Admin الكاملة
    /carrier           ← لوحة Carrier
    /shipper            ← لوحة Shipper
  /components
    /shared            ← أزرار، شارات الحالة، عناصر مشتركة عبر الأدوار
    /shipment           ← مكوّنات خاصة بعرض/تعديل الشحنة
  /services
    api-client.ts       ← طبقة اتصال موحّدة بالـ API (Base URL, معالجة الأخطاء الموحّدة)
    workflow-ui.ts       ← ⚠️ منطق "أي أزرار تظهر لأي دور بأي حالة" — يُشتق من نفس تعريف API Specification، لا يُعاد اختراعه
  /state
    auth-store            ← حالة تسجيل الدخول والدور الحالي
    notifications-store    ← عدّاد الإشعارات غير المقروءة (Polling أو WebSocket لاحقًا)
```

## 3. مبدأ توحيد منطق الأزرار مع الـ Backend

**مشكلة يجب تفاديها:** لو كتبت الواجهة شروط "متى يظهر زر (بدء الشحن)" بمنطق منفصل عن Backend، فسيختل الاتساق فور أي تعديل مستقبلي على تدفق العمل (تصريح صاحب المصلحة، ADR-007).

**الحل المعماري:**
- الواجهة **لا تخزّن قائمة تحويلات مستقلة**. بدلاً من ذلك، استجابة `GET /api/v1/shipments/{id}` تتضمن حقلاً إضافيًا `available_actions` يحسبه الـ Backend مباشرة من وحدة السير المركزية (راجع Backend Architecture، القسم 2):
```json
{
  "id": "uuid",
  "status": "pending_shipper_pricing_approval",
  "available_actions": ["approve_pricing", "reject_pricing"]
}
```
- الواجهة تعرض فقط الأزرار الموجودة في `available_actions` — لا منطق شرطي محلي حول الحالات. هذا يضمن أن أي تعديل مستقبلي في `Backend Architecture` (وحدة السير) ينعكس تلقائيًا على الواجهة دون أي تعديل في كود الواجهة نفسها.

> ⚠️ هذا يتطلب تحديث بسيط في `API Specification.md` لإضافة حقل `available_actions` لاستجابات الشحنة — يُوصى بتطبيقه فور بدء التنفيذ الفعلي.

## 4. إدارة الحالة (State Management)

- **حالة المصادقة:** Token + بيانات المستخدم (id, role, status) تُحفَظ في الذاكرة (لا Local/Session Storage للتوكن الحساس إن أمكن تفاديه؛ أو HttpOnly Cookie إن دعمه الـ Backend — قرار أمني يُحسَم في Backend Architecture لاحقًا).
- **حالة البيانات (شحنات، ناقلون، شاحنون):** تُجلَب عند الحاجة من الـ API مباشرة (لا تخزين محلي دائم يخالف مبدأ "الإدارة لا الأرشفة" — الواجهة تعرض الحالة الحية، لا نسخة مخبَّأة قديمة).

---

## 5. دعم RTL والتدويل (i18n)

- كل النصوص تُسحَب من ملف ترجمة مركزي (`/locales/ar.json`) منذ اليوم الأول، حتى لو كانت العربية هي اللغة الوحيدة المفعَّلة حاليًا — لتفادي إعادة هيكلة عند إضافة الإنجليزية لاحقًا (مواءمة مع نطاق الشركة الأوسع في سنغافورة ومصر، Product Vision).
- اتجاه الصفحة `dir="rtl"` افتراضي على مستوى `<html>`.

---

## 6. الاستجابة لحجم الشاشة (Responsive)

- تصميم Mobile-first بسيط: لوحات Admin/Carrier/Shipper تعمل على الجوّال والحاسوب عبر نفس الكود (Responsive Web)، لا تطبيق جوّال منفصل في MVP (متوافق مع نطاق Product Vision الحالي).

## 7. نقاط تحتاج قرارًا

| # | القرار |
|---|---|
| 1 | إطار العمل المحدد (React؟ Vue؟ غيره؟) — لم يُحدَّد بعد |
| 2 | آلية تحديث الإشعارات: Polling دوري بسيط أم WebSocket مباشر؟ (يُوصى بـ Polling في MVP لبساطته) |
| 3 | مكان تخزين Token (HttpOnly Cookie مقابل الذاكرة) — قرار أمني مشترك مع Backend Architecture |
